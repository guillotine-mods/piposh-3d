# Bug tracker

A working list of known issues, separate from `docs/PLAYTEST.md` (which
tracks asset-level correctness — facing, positioning, camera angles against
the original game) and `docs/SESSION_LOG.md` (the permanent record of *how*
each fix was found and verified, written after the fact). This file is the
*queue*: what's still open, referenced by ID.

**Workflow:** say "let's work on `GB-2`" (or however you refer to it) to
start on an entry. Once a fix ships and you've confirmed it in-game, delete
that row — don't leave it marked "done," just remove it. The fix's own
history stays in `docs/SESSION_LOG.md` and the commit that made it; this
file only needs to reflect what's still outstanding.

**Adding new bugs:** append a row to the right section with the next free
number in that prefix (don't reuse numbers from deleted rows, so an ID
never means two different things across a conversation). A one-line
description is enough — add detail if you have it (which level, what you
expected vs. what happened), but don't feel obliged to.

**IDs:** `GB-*` = game-breaking, `QOL-*` = quality of life, `NB-*` =
non-breaking bugs. Prefix groups are just for scanning; nothing stops a
QOL item from being promoted to GB (or the reverse) by moving the row.

Round 2, after live re-test: (5) pSkip's z-index (50 vs pRIP's 20) was already correct in the built scene but still rendered underneath in real play — z-index alone isn't reliable enough for this project's Control hierarchy on its own; added an explicit post-build tree reorder (sort panels by z-index, `move_to_front()` each in order) as a second, more robust guarantee, matching how `GameHud.show_dialog()` already hedges the same way. (9) that same blind mouse-hunting was ALSO why the aim reset looked like it wasn't working: `mickey` (mouse delta) keeps accumulating every frame regardless of freeze state, so whatever motion happened clicking Retry was still sitting there the instant `action CamTarget` resumed, and got applied on top of the just-reset spawn pose before it ever reached the camera — fixed by clearing the accumulated delta in the same synchronous burst as the pose reset. Round 4 (QOL, user request rather than a new report): added a `Space` key that recenters the aim back to spawn pose at any time (not just on retry), and the OS cursor now warps to the window center whenever it becomes visible (death screen, or a `Space` recenter) instead of being left wherever it silently drifted to while captured. Round 5, after live re-test again ("still not 100% working... the skip button is still beneath the graphic that's shown when we die", "the pointer should be reset after we click to restart, not after we die"): (10) two prior pSkip-vs-pRIP z-order fixes (round 1's z-index default, round 2's `move_to_front()` tree reorder) both should have worked within `GameHud`'s single shared `CanvasLayer` and both still didn't — moved to a mechanism this project already relies on and knows works: `GameHud` now has a SECOND `CanvasLayer` (layer 21, above its own 20) that any button-bearing panel without an explicit `layer` mounts on instead, which always draws over the normal one unconditionally, the same guarantee already used for the loading screen/level-select menu. (11) moved the cursor-to-center warp from the moment `pRIP` becomes visible (death) to the moment it hides again (clicking Retry), per the request. Round 6, after live re-test again ("it spawns correctly in the middle but now 180 degrees back"): (12) `Input.warp_mouse()` (used by both the retry-click and Space recenter) can itself generate a synthetic mouse-motion event reporting the jump it just caused, arriving a frame or two AFTER the warp call — landing in the mouse-delta tracking after the existing same-frame clear had already run, and getting read as a huge real mouse movement on the very next aim tick, spinning the just-reset pose most of the way back around. Sanity-checked the spawn pose data itself first (confirmed correct — faces every Range target). Fixed with a short multi-frame suppression window armed by the warp itself. Found along the way: this port's WDL parser treats `define NAME,VALUE;` as an ordinary global variable, not a real alias — so `define Pop,skill20;` never makes `my.Pop` resolve to `my.skill20`; every named field actually lives in its own `wdl_custom_<name>` meta key. Round 8, after live re-test again ("after the first reset, the character heads are not moving up and shown as they were"): (14) round 7's own fix ERASED every `wdl_custom_*` key instead of restoring a real snapshot — regressed `action Terrorist`'s own one-time `my.OriginalZ = my.z;` init (its resting height, read by both the pop-up and duck-down logic every tick, set once before the coroutine's first `wait()` and never again since the coroutine itself is never restarted on retry). Erasing it left it permanently `0.0` after the first retry, silently breaking the pop-up/duck-down thresholds for good. Fixed by capturing a REAL snapshot of every `wdl_custom_*` key right after each entity's coroutine starts (reflects its own one-time init, since coroutines run synchronously up to their first real `wait()`), and restoring FROM that snapshot on retry instead of erasing. | GB-8 | Range: bullet-vs-target hit detection feels imprecise/unreliable ("the collision isn't working"). | **Fixed 2026-08-07**, pending in-game confirmation. Root cause found via the user's own real shot log (added 2026-08-07): every fired bullet died within a near-constant, aim-independent distance of its target (~180-193 units regardless of where the player aimed) — matching "distance from the fixed shooter position," not an actually-traveled path. Two compounding bugs: (1) `action Spark` enables impact detection as its OWN first statement, before it has moved, and bullets spawn AT the shooter's own position — the impact check's "touching" set starts empty for a brand new zone, so the shooter itself (already overlapping at that exact instant) read as "just walked in" on the very first check and killed the bullet immediately, before it ever traveled anywhere. This is generic, not Spark-specific: ANY entity spawned already overlapping another would hit the same bug. Fixed by pre-seeding the touching set with whatever's already in range at zone-creation time, silently. (2) even with that fixed, bullets kept dying almost instantly against an invisible, non-gameplay "CameraEngine" placeholder (a `Cam.MDL` marker sitting near the shooter's own line of fire, its action doesn't resolve to any real script) — flagged every marker this project already hides for being a pure logic/position helper (camera placeholders, `action Dummy`) as `wdl_non_physical` and excluded those from impact checks too. Verified: `smoke_range_aim_check.gd` now registers a real hit 3/3 runs (was 0/3 before). Round 2, after live re-test again with a fresh shot log ("the further away the terrorist is, the more likely I still can't hit him"): (3) even with both prior fixes, the impact check compares horizontal (XZ) distance only, ignoring height — correct for its original purpose (a walker's Y is artificially pinned to spawn height by a missing floor-snap, unrelated to real geometry), wrong for an actual 3D projectile: a shot aimed at a far target flies over/under any nearer target sitting in roughly the same XZ column at a different height, and since height was ignored that nearer target claimed the shot anyway — more distance simply means more nearer targets/scenery to pass by first. Fixed by using real 3D distance whenever either side of a checked pair has genuinely moved in height from its own spawn position (a bullet in flight, or a target mid pop-up/duck-down); entities that haven't moved in Y keep the original XZ-only behavior, so Shiks' own walker-vs-static-target case is untouched. Verified: `smoke_range_aim_check.gd` hit rate 10/11 across this session's runs (was 0/8 before any GB-8 fixes). Round 3, after live re-test again ("it still doesn't hit far targets accuratley"): (4) re-attempted the original "widen the hit radius to each target's own mesh footprint" fix (tried once 2026-08-06, reverted after a regression) — both root causes of that regression (spurious touch at zone creation, and the XZ-only check letting a wrong-height neighbor claim a shot) are fixed as of rounds 1-2 above, so this time it held: `smoke_range_death_freeze.gd` (the exact test that caught the original regression) now passes with it enabled. Verified hit rate 10/10 across two fresh batches, including several shots (70-90 unit closest-approach) that were misses immediately before this change. Separately noted, not yet addressed: 4 of Range's 20 targets require a tilt angle steeper than `action CamTarget`'s own `[-15,45]` clamp allows (as low as -18°) — authored in the original WDL script itself, not a port bug, but means those specific (closer, not farther) targets are physically impossible to aim at with pixel-perfect precision no matter how the mouse is moved; flagged for awareness, not fixed (would mean deviating from the original script's own clamp). See `docs/SESSION_LOG.md` 2026-08-06 (GB-7 round 6), 2026-08-07 (GB-8 continued, GB-8 fixed, GB-8 round 2, GB-8 round 3). |
